# Dropdown order fix and orchestrator stabilization for PJUD bot

The bot's search flow was failing because it selected dropdowns in the wrong order (Estado before Tipo Causa) and used `document.body.click()` to close them — which on some custom multiselect components deselects the choices. After "Buscar" fired, the portal returned 0 results and the UI reset. This change reorders the dropdowns (Tipo Causa first, Estado second), replaces body-click with Escape-key dismissal, adds a 30-second polling wait for results, and fixes several orchestrator stability issues: removing `page.goBack()`, wiring env vars, fixing the schema CHECK constraint, and calling `markCausaScraped`.

Watch for: The `selectAllInDropdown` heuristic relies on CSS class substring matching (`[class*="select"]`, `[class*="dropdown"]`) which may match unrelated elements on the page (confirmed — the selector is extremely broad). The `stillOpen` check uses `.dropdown-menu.show` and other class-based selectors that assume a specific UI framework; if the portal uses a different pattern, the close-verification will always return false and the dropdown may stay open silently (likely). After scraping a detail, `navigateToConsulta` loses the search results table, so subsequent `navigateToCausaDetail` calls in the loop will fail to find their RIT (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The core fix reorders the two multiselect dropdowns from Estado→Tipo to Tipo→Estado and replaces the close mechanism from `document.body.click()` to `page.keyboard.press('Escape')` with a toggle-retry fallback. The new `selectAllInDropdown` helper centralizes the open→select→close logic, but its element-finding strategy is a broad heuristic that could misfire on DOM structures it doesn't anticipate.

The polling loop replaces the previous `sleep(8000)` for waiting on results. It checks for RIT-patterned cells every 2 seconds for up to 30 seconds. If the portal takes longer to render 16k results, the poll times out and the bot proceeds with zero causas — a false negative indistinguishable from a real failure.

In the orchestrator, `page.goBack()` is replaced with `navigateToConsulta(page)` which re-clicks "Mis Causas" and the Familia tab. This preserves session but loses the search results. Every detail scrape after the first will call `navigateToCausaDetail` against the default (unfiltered) listing, which won't contain the target RIT. The detail loop is effectively broken for items 2–N.

The `tipo` field mapping now only maps 'P' and 'X' (dropping 'C'), satisfying the DB CHECK constraint. `markCausaScraped` is now called after each successful detail scrape. `BOT_MAX_CAUSAS` is read in two places with different semantics: `index.ts` uses it for discovery limits, `orchestrator.ts` re-reads it for detail-scrape limits.

## Dropdown interaction rewrite and order fix

The old code had Estado at PASO 3 and Tipo Causa at PASO 4. The new code flips them to match the user-reported correct sequence: Familia → Filtros → Tipo Causa 5/5 → Estado 12/12 → Año → Buscar.

The `selectAllInDropdown` trigger-finding heuristic walks all elements matching:

```typescript
'select, .multiselect, [class*="select"], [class*="multiSelect"], button[data-toggle], .dropdown-toggle, [class*="dropdown"]'
```

This will match elements like `<div class="unselectable">`, `<span class="selected-count">`, or any element with "dropdown" anywhere in its class list. The fallback path (find by index: first visible = tipo, second visible = estado) partially mitigates this, but the label-matching path runs first. A false match means a wrong element gets clicked, the dropdown doesn't open, and the "Seleccionar Todos" click falls through to the page-wide fallback — which would click the first `Seleccionar Todos` it finds, potentially from the wrong dropdown.

The `stillOpen` check:

```typescript
'.dropdown-menu.show, [class*="multiselect-content"]:not([style*="display: none"]), [class*="open"], [class*="active"]'
```

If the PJUD portal's multiselect uses visibility, opacity, or custom data attributes for open/close state, this check returns false, the dropdown stays open, and the next dropdown interaction will fight with the first one.

## Post-detail navigation breaks the scrape loop

After scraping a causa detail, the orchestrator calls `navigateToConsulta(page)` which clicks "Mis Causas" → Familia tab. This puts the page back at the *default* Familia listing — not the filtered/searched results table. The loop then calls:

```typescript
const rows = document.querySelectorAll('table tr')
for (const row of rows) {
  if ((row.textContent || '').includes(targetRit)) { ... }
}
```

If the search results aren't visible (no search re-executed), the RIT won't be found, `opened` will be false, and the detail scrape is skipped silently. Only the first causa detail will ever be scraped per session.

The fix should either: (a) re-run `searchByYear` after navigating back, (b) store `detailLink` href values from the initial table read and use `page.evaluate(() => { location.href = storedHref })` within the same origin, or (c) implement a "back to results" click if the portal offers one.

## Polling timeout and RIT regex

The polling regex `^[A-Z]?-?\d+-\d{4}$` correctly matches standard Chilean RIT formats (`C-4875-2025`, `P-7940-2026`, bare `44977-2026`). Multi-letter prefixes are unusual in Familia courts but worth verifying against live data. The 30-second timeout is a fixed constant that may not account for the portal's load time when serving paginated responses covering 16,000+ causas. If the server sends results incrementally (the table appears but RIT cells render later), the poll could time out while data is still loading.

## BOT_MAX_CAUSAS applied in two places with different meanings

In `index.ts`, `BOT_MAX_CAUSAS` sets `config.maxCausasPorSesion` (limits how many causas are listed from the portal). In `orchestrator.ts`, the same env var conditionally overrides `cfg.maxDetailsPorSesion` (limits how many detail pages are scraped). Setting `BOT_MAX_CAUSAS=20` means "discover max 20 causas AND scrape max 20 details" — but only if 20 < the configured `maxDetailsPorSesion` (50). If the intent is two separate knobs, they need two env vars (`BOT_MAX_CAUSAS` + `BOT_MAX_DETAILS`).
