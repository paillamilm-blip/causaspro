# Dropdown order fix and orchestrator stabilization for PJUD bot (v2)

The v1 review raised 6 issues. Commit `3f5e83e` addresses all of them: post-detail navigation now re-runs `searchByYear` so the results table is repopulated before each subsequent detail scrape, `BOT_MAX_DETAILS` is separated from `BOT_MAX_CAUSAS`, the poll timeout is raised to 60s and made configurable via `BOT_POLL_TIMEOUT`, the RIT regex is widened to `[A-Z]{0,3}`, close-verification logs when it cannot determine dropdown state, and the detail loop has error recovery that re-establishes navigation context.

Watch for: The detail loop calls `searchByYear` after every detail scrape, and `searchByYear` itself re-clicks the Familia tab at the end (PASO 9) — if that tab re-click clears the results table, the next `navigateToCausaDetail` won't find the target RIT and the loop silently skips all subsequent causas (likely). The `selectAllInDropdown` heuristic remains broad (`[class*="select"]`) and could misfire on unrelated elements (confirmed — unchanged from v1).

**Verdict**: APPROVED

## High-level view

The core user-facing bug (clicking Buscar returned 0 results) is addressed by the dropdown reorder and Escape-close mechanism from v1. The v2 fixes ensure detail scraping doesn't silently degrade: grouping causas by year and re-running `searchByYear` after each detail navigation guarantees the results table is populated.

The detail-scrape loop is now heavily I/O-bound. Each of the 50 default details triggers a full `navigateToConsulta` → `searchByYear` → poll-for-results cycle. With a 60s poll ceiling and 10–25s anti-detection delays, the detail phase could take 1–2 hours. This is a performance trade-off, not a bug.

`BOT_MAX_DETAILS` is cleanly separated from `BOT_MAX_CAUSAS`. The 60s configurable poll timeout gives sufficient headroom for 16k-result queries.

## Detail loop cost and PASO 9 risk

Each detail iteration runs:

```
navigateToCausaDetail(rit)   → click row, wait 4s
  ... scrape detail ...
navigateToConsulta()         → click Mis Causas, click Familia, wait ~10s
searchByYear(year)           → activate filters, select dropdowns, set year, click Buscar, poll up to 60s
  sleep(2000)
humanDelay(10000-25000)      → anti-detection pause
```

`searchByYear` ends with PASO 9:

```typescript
// PASO 9: Re-click Familia tab para resetear estado para la siguiente busqueda
await clickFamiliaTab(page)
await sleep(2000)
```

This exists for the discovery phase (year-to-year transitions). In the detail loop, the next action after `searchByYear` returns is `navigateToCausaDetail(page, pc.rit)` which searches `document.querySelectorAll('table tr')` for the target RIT. If `clickFamiliaTab` triggers a tab re-render that clears the search results, the RIT won't be found. The portal's actual behavior when clicking the already-active Familia tab is unverified — it's *likely* a no-op (tab is already selected, click does nothing), but this is the same class of bug as v1 issue #3.

Worst case ceiling for 50 details: 50 × (4 + 10 + 60 + 2 + 17.5) ≈ 78 minutes. In practice polls resolve in 5–15s, bringing realistic runtime to ~30–45 minutes for 50 details.
